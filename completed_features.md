## P02-RENDER: `Register_For_Rendering` and `Set_User_Lighting_Flag` implemented

Both are declaration-only in the donor; the bodies were derived from the stock
code they sit beside, not taken from TT.
- `Set_User_Lighting_Flag` sets `HAS_USER_LIGHTING` bottom-up from what an object
  holds (a mesh's lighting array, or a flagged sub-object). The vertex solve used
  to flag every object it visited top-down, so terrain patches (which keep their
  solve as vertex colours) and unlit models went into the light-solve save as
  empty chunks. `LightSolveClass::Compute_Solve` and both `Load_User_Lighting`
  paths call it now.
- `Register_For_Rendering` does ahead of time what `MeshClass::Render` did on a
  mesh's first visible frame: register it with the DX8 mesh renderer. It recurses
  sub-objects and needs a device. `GameInitMgrClass` runs it over the static
  world after the post-load renderer invalidate, behind the load screen. TT's
  `hint_static` parameter is dropped: the DX8 renderer already picks static or
  dynamic buffers by the skin flag, so nothing would read it.

## V2 Phase 3 -- the procedural boundary cliff ring, and the world owner that drives it

`BoundaryCliffGenerator` (`Code/wwphys/boundarycliffgenerator.h/.cpp`) builds the continuous
cliff ring that gives Phase 2's invisible hard boundary a physical explanation (Sections 5.3-5.5,
5.9, 28). Four of the five components Phase 3 names already existed in this tree, so the phase's
own "create **or adapt** something equivalent" was taken the second way: `EscarpmentClass` --
whose header already opens "the vertical face a heightfield cannot hold" -- supplies the spline,
`EscarpmentSystem::Build_Escarpment_Geometry` (on the shared `DynamicMeshBuilderClass`) the
segment mesh, its `StaticPhysClass` the collision, and `TERRAIN_LAYER_CLIFF` +
`MATERIAL_PROGRAM_TERRAIN` the material. Writing a second cliff mesh path would have been the
parallel implementation this project forbids and would have left two answers to "is there a wall
at x,y".

The ring is **many escarpments, not one**: Phase 3 refuses to proceed if the ring is a single
monolithic unbounded mesh, and an escarpment is one mesh and one collider, so the whole perimeter
handed over as one escarpment would have been exactly that. It is cut into chunks of 16 stations,
and chunk *k*'s last station is the **same entry of one canonical array** as chunk *k+1*'s first
-- two chunks cannot drift apart because neither owns the number. The last chunk closes onto
station 0, which is why the array carries no duplicate closing station.

Direction is load-bearing: an escarpment drops to the right of travel and `WorldBoundsService`
normalizes to clockwise, whose interior is to the right of every edge, so walking in polygon
order drops the face **inward** and builds a basin rather than a mesa.

`Build_Ring` splits into `Plan_Ring` (stations, chunks, checksum -- no device, no scene) and
`Realize_Ring` (meshes and colliders, needs a `PhysicsSceneClass`). Every property the phase
cares about is a property of the plan, so a device-less check can hold the ring to all of them.
A failed realization leaves **no** ring: half a ring is the traversal leak the phase exists to
prevent, invisible from inside.

`ProceduralWorldManager` (`Code/Combat/proceduralworldmanager.h/.cpp`) is the procedural-world
owner Phase 3 step 1 refers to and the first phase to actually need one: `Request_World` before a
level load, `Generate_World` from `CombatManager::Post_Load_Level`, `Destroy_World` from
`Pre_Load_Level`. With no request outstanding it returns immediately having configured nothing,
which is every hand-authored map (directive 1.10). Boundary is configured before cliffs, so a
cliff failure still leaves the world correctly closed.

Schema moved to version 2: Section 5.5's `rim_roughness`, `face_roughness`, `toe_width` and
`collision_simplification`, plus `world.fit_to_level` and `world.center_x`/`center_y`.
Generator version moved to 2 independently -- the same seed and the same schema-1 profile now
produce a world with cliffs where before it produced an invisible boundary. A schema-1 profile
still loads. Shipped profile: `data/procedural_world/default.json`.

`fit_to_level` sizes the world from `PhysicsSceneClass::Get_Level_Extents` and makes it **larger**
than the host level by the full band inset, so the entire authored level stays in
`PLAYABLE_INTERIOR` and the cliffs stand on the empty ground beyond it. The cliff foot takes the
level's own floor. The manifest records the profile as *used*, not as authored.

`EscarpmentClass` gained `FaceRowCount` (default 1), `ToeWidth` (default 0) and
`EscarpmentPointClass::FaceInflection` (default 0) -- all additive, all defaulting to byte-identical
previous geometry, so existing hand-placed escarpments are unaffected. `Clear_Ring` preserves
authored escarpments.

Step 11 is real: `WorldTerrainSystem::Modify_Height_Region`, `Apply_Road_Grade` and
`Apply_River_Cut` now refuse edits inside the cliff band, asking
`WorldBoundsService::Can_Place_In_Region` -- the same question building placement asks -- rather
than inventing a second notion of where the band is. The polyline mutators skip offending stamps
rather than rejecting the call, so a river approaching the perimeter terminates there, which is
Section 5.9's own instruction. Steps 12/13 were already satisfied by Phase 2; step 14 has nothing
to reject until Phases 8-10 create procedural roads/tunnels/bridges.

Step 15's three diagnostics (`Check_Seam_Continuity`, `Check_Inverted_Triangles`,
`Check_Traversable_Ramps`) run on the canonical stations. Render gap and collision gap are the
same question asked once, because an escarpment's collider is the mesh it draws. Step 16 is
`debug_layer boundary_cliffs 1` -- rim line, toe line and a per-station riser coloured green for
a wall and red for a climbable face. Step 17 is `WorldGenerationManifest::CliffRingChecksum`.

New seed domain `boundary_cliffs`, deliberately separate from `boundary` so rim noise is not
correlated with the polygon that noise is wrapped around. Rim noise is smoothed three times
circularly, which is not cosmetic: raw per-station noise puts a tall station beside a short one,
which is the shape a climbable notch has.

**Main menu button "Procedural Skirmish"** (`IDC_MENU_START_PROCEDURAL_GAME_BUTTON`), between
Practice and Options. It takes the same skirmish map the Practice button picks and places a world
request before starting it -- a procedural world is laid *over* a real level, since the generator
owns the boundary and the ring while lighting, spawners, presets and the physics scene still come
from the level. The label is a literal string rather than an `IDS_` id, because

## V2 Phase 6 -- hydrology, and the one water renderer used a second way

`HydrologyGenerator` (`Code/wwphys/hydrologygenerator.h/.cpp`) is the missing caller
`WaterSystem`'s own documentation named and left for later: "nothing plants anything... reading
water areas out of a level's own data is a level-format question, not this one." This generator
computes drainage and hands the result to `WaterSystem::Add_Area`/`Shape_Terrain`/`Stamp_Mask`/
`Build_Geometry` -- the same entry points the console command and self check already used. No
second carving primitive exists; `WorldTerrainSystem::Apply_River_Cut` (used internally by
`Shape_Terrain`) is untouched.

Drainage is computed at chunk resolution, not vertex resolution -- a real per-vertex D8
simulation was not attempted, the same honest scoping choice Phase 5 makes about ridge-line
extraction. One representative height per chunk; steepest-descent flow direction among four
neighbours, never toward a `CliffBand` chunk (Phase 6 step 2, kept structurally: a cliff-band
neighbour is never a candidate flow target at all); accumulation summed in one height-descending
pass, the standard sorted-list D8 algorithm. A chunk with no lower non-cliff-band neighbour is a
sink/basin. A channel-eligible chunk nothing else channel-eligible flows into is a headwater;
headwaters are walked chunk-to-chunk in accumulation-descending order, bounded at
`water.max_river_count`, until each reaches a sink or joins an already-built channel. Peak
accumulation along the path decides river versus stream (Section 9.2 treats both as one network,
gated by one `water.rivers` flag); width grows with accumulation per station
(`lerp(stream_width, river_width, accumulation/river_accumulation_chunks)`); station height is a
real `WorldTerrainSystem::Sample_Height`, clamped non-increasing against the previous station as
a defensive backstop, so the guarantee `Check_River_Never_Climbs` proves is one `Generate`
actually keeps.

**Section 5.9, kept structurally, not by a check.** A channel can never reach the cliff band
because a cliff-band chunk is never a flow target in the first place; the chunk whose only lower
neighbours were cliff-band becomes an ordinary sink instead, and the channel terminates there as
a real, visible enclosed lake/pond -- one of Section 5.9's own four named options. With both
`water.lakes` and `water.ponds` disabled, the channel simply stops carving at the sink with
nothing built past it, satisfying "no unexplained traversable hole" because there is no channel
there to have left one. A lake/pond's own carve deliberately overlaps a river's terminal station
(the river runs into the lake's own shore rather than stopping short of it) -- one accepted,
documented consequence: a point query exactly at that overlap currently favours whichever area
was placed first.

A sink's own accumulated inflow decides lake versus pond, the same threshold already meaningful
for river/stream, not a second arbitrary number. A basin is a closed ring matching its own
chunk's square footprint, at its own sampled minimum height plus a small margin -- a coarse,
documented approximation of a basin's true shape, the same per-chunk granularity Phase 5's own
stations already accept. Depth is deliberately not a new profile field:
`WaterDefinitionClass::BedDepth`, already set per category by `WaterSystem::Define_Default_
Water`, is carve depth's one source of truth, so a second number could only ever disagree with
it.

Shore classification (`WALKABLE_BANK`/`STEEP_BANK`/`CLIFF_SHORE`/`VEHICLE_CROSSABLE`/
`NON_CROSSABLE`, Section 9.3/9.5) is one real `WorldTerrainSystem::Sample_Slope` measurement per
feature against two fixed thresholds, overridden by width for the vehicle/non-crossable cases --
measured, not hashed, unlike Phase 5's per-feature traversability draw, since real slope/width
data is available here. Every feature records exactly one crossing candidate: `FORD`/`BRIDGE`
for a channel by width, `ROUTE_AROUND` for an enclosed basin. `TUNNEL` stays a legal value this
generator never picks -- that judgement is explicitly Phase 10's, not a hydrology pass's.
Building the actual crossing infrastructure is out of scope here too (Phases 8-10).

Schema moved to version 4: four new `water` fields (`river_width`, `stream_width`,
`river_accumulation_chunks`, `max_river_count`); generator moved to 4 independently.
`water.coastline` (Section 9.4, optional) is parsed since Phase 1 and still unconsumed -- the
same "reserved, unconsumed" state `interior_cliff_density` was in before Phase 5; true watershed
boundary delineation was not attempted either. New debug layer `DEBUG_LAYER_HYDROLOGY`/
`debug_layer hydrology 1`, drawing for real from the moment it exists. New
`WorldGenerationManifest::HydrologyChecksum`. No new seed domain -- `SEED_DOMAIN_HYDROLOGY` was
already reserved.

`terrain_hydrology`/`fds_terrain_hydrology` (`-terrainselfcheck hydrology`) prove, against the
same synthetic uniform-slope ramp `Check_Interior_Cliffs` uses (for the identical reason: a real
generated seed's relief gives no arithmetic guarantee a channel or basin exists to check
against): parameter refusal; a river and a lake both built with every structural diagnostic (no
cliff-band overlap, no climbing river station, no lake above its own basin rim, every feature
carries a crossing candidate) holding; same seed reproduces the same checksum; and a configured
boundary's cliff-band chunks are never reached by a channel or its terminal basin. `ctest -N` now
lists 141 (was 139). `renegade`, `renegadeserver` and `leveledit` all build clean, 0 warnings.
Docs: `docs/procedural_world/Hydrology.md` (new), Phase-6 sections in
`GeneratorDeterminism.md`/`WorldProfileSchema.md`, `docs/zerohour/DebugRenderSystem.md` updated
for the new `hydrology` consumer.

## V2 Phase 7 -- strategic planning, a candidate pool that chooses nothing

`StrategicPlanner` (`Code/Combat/strategicplanner.h/.cpp`) produces Phase 7 step 9's abstract
node graph -- `BASE_CANDIDATE`/`RESOURCE_CANDIDATE`/`SETTLEMENT_CANDIDATE`/`POI_CANDIDATE`/
`CROSSING_CANDIDATE`/`TUNNEL_CANDIDATE` -- as a scored pool for a later phase to choose from.
Step 12 is explicit that nothing gets chosen yet, and `WorldGenerationManifest::
SelectedBaseCandidateIds` and its four siblings (named "Selected") stay empty from this phase,
kept honestly distinct from the new `StrategicPlanChecksum` field, which is a checksum over the
full candidate pool, not a claim anything was picked from it.

**Reuse, not rediscovery.** Phase 5's interior cliff bypass candidates and Phase 6's hydrology
crossing candidates fold straight into this graph -- `BRIDGE_CROSSING`/`TUNNEL_BYPASS` interior
cliff features and `FORD`/`BRIDGE` hydrology crossings become `CROSSING_CANDIDATE`/
`TUNNEL_CANDIDATE` nodes, never re-derived from the terrain a second time; a hydrology
`ROUTE_AROUND` candidate is a routing hint, not infrastructure, and gets no node. Water/cliff
exclusion (step 1) reads `WaterSystem::Is_Point_In_Water` and the chunk registry's own
`Buildable` flag directly rather than testing either fact twice.

Suitability collapses step 1's six named inputs into what is actually measurable: `Buildable` +
`Is_Point_In_Water` as a hard eligibility gate; `WorldBoundsService::Get_Inward_Distance`,
normalized, for boundary distance; how many of a chunk's own four neighbours are themselves
eligible as one proxy for reachable-area/expansion-room/roadability, which doubles as step 4's
own approach-count rejection test (threshold sourced from `fairness.min_vehicle_approach_count`,
already validated, never a second invented number); and, for base candidates only, a proximity
bonus toward the nearest Tiberium candidate. A small deterministic hash jitter (weight 0.05) is
the seed's only real job here -- every ranking is otherwise a pure function of the terrain, and
without it two seeds over similar terrain would break every tie identically.

**The step 1/5/11 ordering problem, resolved explicitly.** Suitability wants resource proximity
as a base-scoring input; step 5 places Tiberium after bases; step 11 wants Tiberium checked for
a nearby base after bases exist. Resolution: Tiberium *candidate positions* are chosen first (by
terrain score alone, not yet nodes); bases are scored against those positions and accepted
alternating GDI/Nod (a faction that reaches its own target yields its slot to the other rather
than wasting a candidate); only then does a Tiberium position become a real `RESOURCE_CANDIDATE`
node, and only if a base landed within `max_economic_range` of it -- step 11's "eliminate
candidate combinations that are obviously economically disconnected", made concrete. Settlement
and POI candidates use plain terrain score on whatever remains claimed; forward expansion/
outpost candidates (step 8) are their own pass scored by *distance from the nearest base*
instead, filed as `POI_CANDIDATE` since step 9's own closed vocabulary has no separate slot for
them -- stated here rather than silently assumed. Step 10's travel-cost graph is exactly what it
says: an N×N straight-line distance matrix, not a routed cost, which needs Phase 8's road graph
to compute.

No new profile fields and no schema bump -- `fairness.min_vehicle_approach_count` was already
there and already validated. `terrain_strategic`/`fds_terrain_strategic`
(`-terrainselfcheck strategic`) prove, against a large synthetic uniform-slope ramp built with
plenty of eligible, dry, unconfigured-boundary room for every category at once: parameter
refusal; each faction reaches the targeted validation's own floor of 2 base candidates; at least
1 Tiberium candidate survives the economic-range filter; no node overlaps water or the cliff
band; no resource candidate is economically disconnected; every base candidate carries a real
`PLAYERTYPE_GDI`/`PLAYERTYPE_NOD` faction; the travel-cost matrix is symmetric and zero to
itself; and the same seed and terrain reproduce the same checksum. `ctest -N` now lists 143 (was
141). `renegade`, `renegadeserver` and `leveledit` all build clean, 0 warnings. Docs:
`docs/procedural_world/StrategicPlanning.md` (new), Phase-7 section in `GeneratorDeterminism.md`.

## V2 Phase 8 -- road graph, realized through the one road system

`RoadGraphGenerator` (`Code/Combat/roadgraphgenerator.h/.cpp`) decides which strategic anchors
(`BASE_CANDIDATE`/`RESOURCE_CANDIDATE` nodes) need a road between them -- a minimum spanning
tree over `StrategicPlanner`'s own straight-line travel costs, bounded at N-1 edges -- then finds
a real, terrain-costed route for each via Dijkstra over the chunk grid and hands it to
`RoadSystem::Add_Road`/`Build_Network`, the same entry points the console command and self check
already used. No road geometry of its own; `RoadSystem` (v1, complete) owns all of it.

**Six conceptual classes, three physical ones.** Section 10.1 names six road classes; v1's
`RoadClassType` has three, already tested, and extending it purely to grow a name list would
touch `BridgeSystem`'s own default class mapping for no reason this phase needs.
`RoadGraphClassType` is Section 10.1's own six names, used only for this file's own cost-field
weighting and default width; mapped down to `RoadClassType`'s three for the question
`RoadSystem` actually asks. Default widths are fixed constants, not Section 10A.1's real
Humvee-derived formula -- that needs naming a specific vehicle definition, the kind of
enumerable identifier this project does not guess.

The routing cost field reuses Phase 7's own exclusion tests directly: a `CliffBand` chunk is
always blocked; an `InteriorCliff` or wet (`WaterSystem::Is_Point_In_Water`) chunk is blocked
*unless* a `CROSSING_CANDIDATE`/`TUNNEL_CANDIDATE` `StrategicNode` sits there, in which case it
costs extra rather than being impassable -- Section 10.3's "bridge/tunnel candidate cost," made
concrete. Every chunk that lifted its block this way is recorded on the edge's own
`UnresolvedCrossingIds` (Phase 8 step 15), per edge rather than one global bag, so Phases 9/10
know which road needs which crossing. An MST edge that cannot route under this cost field is
simply not built rather than silently forced through -- do-not-proceed's "required nodes
disconnected without an explicit pending edge" is kept by counting, not by hoping.

Intersections cost nothing extra: `RoadSystem::Build_Network` already finds and builds junction
polygons for any roads that meet. Not attempted: parallel infantry corridors (step 12), lane-level
modelling (`RoadSplineClass` has no lane-count field to model with), off-road traversal
classification (10A.8), and real route independence (17A.2) -- a spanning tree gives each anchor
exactly one path by construction, never an alternate one.

No new profile fields, no schema bump. `WorldGenerationManifest::RoadGraphChecksum` (reserved
since Phase 1, "0 until Phase 8 exists") is populated now; unlike Phase 7's candidate ids,
`SelectedRoadGraphEdgeIds` genuinely means selected here, since a road graph edge is a road
`RoadSystem` actually built, not a proposal. `terrain_roadgraph`/`fds_terrain_roadgraph`
(`-terrainselfcheck roadgraph`) prove, against a real strategic plan built over the same large
synthetic uniform-slope terrain Phase 7's own check uses: parameter refusal; the anchor nodes
spanned (edge count meets the N-1 floor); no cliff-band crossing; no unresolved water passage;
`RoadSystem::Is_Network_Built` true; and determinism. `ctest -N` now lists 145 (was 143).
`renegade`, `renegadeserver` and `leveledit` all build clean, 0 warnings. Docs:
`docs/procedural_world/RoadGraph.md` (new), Phase-8 section in `GeneratorDeterminism.md`.

Phase 8 carries the same reachability gap every phase since 4 does, now gated one step further:
this generator only runs when the strategic plan itself ran, which only ever happens when macro
terrain ran, which today is never, since the one caller that exists always requests
`fit_to_level`.

## V2 Phase 9 -- bridge planning, realized through the one bridge system

`BridgePlanner` (`Code/Combat/bridgeplanner.h/.cpp`) consumes exactly `RoadGraphGenerator`'s own
`UnresolvedCrossingIds` per edge -- never re-deriving which roads need a crossing -- and calls
`BridgeSystem::Add_Bridge`/`Build_Layout`/`Build_Geometry`/`Set_Damage_State`/`Connect_Roads`,
the same entry points the console command and self check already used. No bridge geometry of its
own; `BridgeSystem` (v1, complete) owns all of it, including the three default bridge kinds
already sized to v1's three road classes (`Define_Default_Bridges`, called automatically by
`BridgeSystem::Init`), so no new bridge definition was authored.

**Finding the banks is a real walk, not a guessed width.** `Find_Bridge_Banks` steps outward
from a crossing point along the perpendicular of the nearest road's own local tangent, testing
at each step whether the obstruction (`WaterSystem::Is_Point_In_Water` for water,
`EscarpmentSystem::Sample_Face` for an interior cliff -- re-derived from the point itself, since
neither Phase 5 nor Phase 6 tags a crossing candidate's own source generator) is still there.
Bounded, so a crossing whose obstruction never clears is step 3's own "reject impossible
bridges" -- left unresolved rather than forced.

**Deck height is Section 11A.2's real formula where real data exists for it.** For a water
crossing, `deck_height = max(0, water_height + clearance_margin + deck_depth - higher_abutment)`
using a real `WaterSystem::Get_Water_Height` -- the lowest elevation that actually clears the
water, never more. For an interior-cliff crossing, `deck_height` stays 0: the two banks are
already the toe/rim heights the cliff itself was built at. 11A.2's own iterative fallback chain
(shift the crossing, lengthen approaches, lower the deck, alternate candidate) is not
implemented -- a rejected span stays unresolved.

Initial damage state is one deterministic hashed draw per bridge, weighted heavily toward
`PRISTINE` (fixed cumulative thresholds, no profile field for this exists). Step 10's "unless an
alternate route exists" is read conservatively: `CountsAsConnectivity` is simply false for every
initially-`BROKEN` bridge, since real alternate-route detection needs the same route-
independence analysis (17A.2) Phase 8 already deferred. Step 11's nav/damage hook is free --
`WorldTraversabilityGraph` (Phase 65) already reads live `BridgeSystem` state every time it is
built, the same "ask the one shared system" integration Phase 5's interior cliffs get for free
from the same graph.

**What is honestly not resolved: step 6, road-to-bridge handoff.** The road a bridge crosses
under still runs through as one continuous Phase-8 centre line rather than being split and
re-terminated at the bridge's own abutments -- `RoadSystem` has no way to remove/split an
already-added road, and rebuilding Phase 8's roads to pre-split at every crossing is scope this
phase does not take on. The bridge itself is real and correctly placed; what is missing is a
caller at that exact point knowing to prefer `BridgeClass::Conform_Point` over the ground.
`Connect_Roads` is still called (correct, forward-compatible) but currently finds nothing to
bind. Strategic importance (step 12) is storage-only, no AI Commander consumer yet.

No new profile fields, no schema bump. `WorldGenerationManifest::BridgePlanChecksum` (new) and
`SelectedBridgeCandidateIds` (populated for real, same as Phase 8's road edges -- a resolved
bridge is a real object, not a proposal). `terrain_bridgeplan`/`fds_terrain_bridgeplan`

## Unattended ctest unblocked -- two real defects behind the modal assert dialog

A full-suite `ctest` run used to stop dead on a modal Abort/Retry/Ignore box that no test runner
can answer and that re-opened on every Ignore. Both causes were real and are fixed.

**Refcounted objects with automatic storage.** `shaderselfcheck.cpp` declared `CameraClass
camera;` on the stack in six checks. `CameraClass` is a `RenderObjClass`, which is a
`RefCountClass`: the constructor starts the object at one reference and the destructor asserts
that reference is gone, so every one of those tripped `refcount.h:185 (NumRefs == 0)` at scope
exit. The engine itself never stack-allocates one -- a grep of the whole tree finds these six and
nothing else. Now `NEW_REF`'d and released before return, per refcount.h's own stated ownership
rules (`RenderInfoClass` keeps a plain reference and never add-refs, so releasing after its last
read is correct). That alone restored `shader_particles`, `shader_weather`, `shader_tracers` and
`shader_debris` on both binaries.

**No assert handler on the self-check entry points.** `WWDebug_Assert_Fail` falls back to a modal
message box when no handler is installed. The game installs one in `init.cpp`, and every other
harness in this tree (`Code/Tests/PhysTest`, `MeshTest`, `movietest`) installs its own; the five
`-*selfcheck` paths return long before `Init` runs and were the only harnesses left without one.
They now install a handler that prints `ENGINE ASSERT: <file> (<line>) Assert: <expr>` to stderr
and exits non-zero -- an engine assert now fails the test loudly, with the diagnostic in the log,
instead of blocking on human input. It deliberately never returns, since `WWASSERT`'s callers all
carry on as though the asserted condition held.

Full suite now runs unattended end to end: 167 tests, 30 failing, every failure reported as text.

## V2 Phase 18 -- runtime terrain mutation and the ordered WorldOperation journal

All sixteen steps built for real. `renegade`, `renegadeserver` and `leveledit` all build clean with
zero warnings; `terrain_worldops` and `fds_terrain_worldops` pass and `ctest -N` is now 175, was
173. Full account: `docs/procedural_world/WorldOperationJournal.md`.

**Step 1 -- the versioned envelope** (`Code/Combat/worldoperation.*`). `WorldOperationClass` carries
a format version, a monotonic operation id, the base revision the submitter measured against, the
type, the team, a server timestamp, one region, and a bounded polyline for the two types that carve
along one. Parameter validation is per type and contains no terrain code at all, so a client can
reject a malformed envelope it will never apply. The wire format is written field by field,
little-endian -- a memcpy of the class would tie the format to one compiler's padding.

**Step 2 -- the world revision.** Owned by `WorldOperationJournal`, which also owns the ordered
operation list and the base terrain snapshot, because splitting them would allow a revision no list
explains or a list no base can be replayed from. `Begin` sets revision 1, not 0: zero means "no
journal", so an operation submitted against 0 is a submitter that never read one.

**The design decision the whole phase rests on:** operations travel, heights never do. A peer
receives the request that produced the terrain and performs it itself; a crater is a fixed ~56 bytes
whatever its radius. One base snapshot at `Begin` pays for three separate features at once --
RESTORE_REGION gets something real to restore from with no per-operation undo blob, replay gets a
defined starting point, and replication stays compact.

**Steps 3-4 -- ten types with per-type dependency masks and per-type protected-region rules.** Every
type invalidates render, collision and nav because every type moves ground; water, roads and
materials differ by type. LOWER and CREATE_CRATER are deliberately the same arithmetic -- a crater
*is* a bounded lowering, and what makes it a crater is step 15's rules, not a second falloff to keep
in step with the first. Protected-region rules had to become per-type because carving a channel is
*supposed* to move water while still being forbidden a bridge abutment, which is why
`GeneratedWorldPlacementRules` gained `Get_Static_Feature_Mask`; `Classify_Static_Features` is now
the lowest set bit of that mask, so the two can never disagree about what is present.

**Steps 5-13 -- reserve, apply, invalidate, commit, journal.** Chunk reservation is all-or-nothing
and is held from before the mutation until after the last dependency commits. Stale-revision
rejection is applied only to the four relative types, which is the roadmap's own "where ordering
matters". Every dependency is driven through the system that owns it and nothing is recomputed in
the journal; a dependency whose system is absent reaches its commit point trivially and says so
rather than pretending work was done. The revision advances last, because a peer that sees revision
N+1 is entitled to ask the pathfinder about revision N+1's ground.

**Step 15 -- bounded crater rules.** Max radius, max depth, a rate limit that reads the journal
rather than a counter (a counter would not survive a replay, and a replay that hit the limit
differently would not be a replay), and no cliff-band mutation -- applied to every type, not only
craters, and refused with a readable answer rather than the terrain owner's silent no-op.

**Step 16 -- `worldop` console command.** `status`, `begin`, `replay`, `crater` and `restore`.
`worldop replay` prints the terrain checksum before and after replaying the journal from the base
snapshot and whether they MATCH, which is the phase's own acceptance line made runnable by a person.

**Three new canonical terrain primitives**, all in `Code/wwphys/` beside the existing ones because
the ground has one owner: `HeightfieldClass::Smooth_Height_Region` (+ `WorldTerrainSystem::
Apply_Smooth`), `WorldTerrainSystem::Apply_Flatten`, and `WorldTerrainSystem::Apply_Height_Patch`
for RESTORE_REGION. The smoother reads every neighbour from the heights as they were before the
operation began -- filtering in place would make each vertex depend on the sweep order, which is the
difference between an operation that replays identically on every peer and one that does not.

**One thing the self-check taught:** smoothing a plane is correctly a no-op. The first version of
the check ran SMOOTH over the uniform test ramp and asserted the ground changed; it did not, and the
code was right -- a linear ramp is already its own four-neighbour mean. The check now digs a real
dent and asserts it gets *shallower*, which is what the operation promises; an assertion that some
bytes changed would have passed on a smoother that did the wrong thing.

**Disclosed gaps:** replication is the format, not the transport -- `Write_Block`/`Read_Block` are
proven by round trip but no packet type sends one yet, which is Phase 19's business where the
snapshot and late-join formats it must sit beside are defined; the journal lives in memory, with
persistence likewise Phase 19's; nav rebuild is whole-world, inherited from Phase 16; and the crater
limits are not yet a profile block, because the roadmap does not ask for one at this phase.

**What is not proven:** that two processes agreed. The self-check runs one journal in one process,
so it demonstrates determinism under replay -- the necessary half. "Server applies, client
reconstructs, collision matches" needs two peers and a transport, and that half is carried forward
to Phase 19 and stated as such rather than claimed.

**Regression status:** full suite 175 tests, 30 failing -- the same 30 names as before Phases 17 and
18, so zero regressions from either.

## V2 Phase 19 -- snapshots, checksums, late join, regional repair, developer rollback

All nineteen steps built for real. All three binaries build clean with zero warnings;
`terrain_worldsync` and `fds_terrain_worldsync` pass and `ctest -N` is now 177, was 175. Full
account: `docs/procedural_world/SnapshotsAndLateJoin.md`.

**Steps 1-7** (`Code/Combat/worldsnapshot.*`). A chunk snapshot holds the difference between a chunk
and the chunk a client can already regenerate for itself -- step 3's own wording read literally,
which is both the simplest thing to implement and the smallest thing to send. Per-chunk and
world-level checksums, dirty-chunk detection against the journal's baseline, a three-threshold
compaction policy (count/age/bytes), and `WorldOperationJournal::Rebase` as the fold. `Compact`
captures before it rebases, because rebasing makes every chunk pristine by definition and a capture
taken afterwards would be empty with the world's history gone.

**Steps 8-16 and 19** (`Code/Combat/worldsyncservice.*`). The handshake carries generator version,
profile hash, content hash, manifest revision, snapshot inventory, snapshot revision, world revision
and world checksum, and refuses the join on any of the first four before a snapshot byte moves. The
join is an explicit state machine rather than one call, because "the baseline did not match" and "a
snapshot was refused" need different recoveries. Regional repair returns one chunk's snapshot and
reverifies it rather than trusting it. Metrics are counted bytes, never estimates.

**Steps 17-18.** Developer rollback, bounded at eight points. The journal is rebased onto the
rolled-back ground rather than rewound -- rewinding would need every operation since the point to be
individually invertible, and a SMOOTH destroys the information needed to un-smooth it.

**Three real defects found by the self-check and fixed, each a genuine design error rather than a
typo:**

1. **A derived value in a checksum is fragility without information.** The chunk checksum folded in
   the chunk registry's entry. That entry is derived from the same heights, so it added nothing --
   but it added sensitivity to sub-millimetre noise, because a client rebuilds from quantized
   heights and the registry truncates float-derived slopes at 1e-3. The ground agreed, the entry did
   not, and the repair protocol cannot tell that from real corruption. Removed; the checksum is
   heights only.
2. **The quantizer has to round-trip exactly.** `Quantize(Dequantize(q))` must equal `q`, and
   truncation breaks it: `2.999f * 1000.0f` is 2998.9998 in float. Rounded, with the division in
   double.
3. **A late joiner has to adopt the authority's revision.** Its ground reaches the server's without
   one operation passing through its journal, so its revision would sit at 1 while its ground was at
   the server's N -- and step 16 gates building and AI state on exactly that number.

**One design correction the roadmap's own wording pointed at:** step 14 says the server "returns only
affected chunk snapshot", and the definite article is load-bearing. `Build_Repair_Block` returns the
*retained* snapshot, not a fresh capture: after a compaction every chunk is pristine against the new
baseline, so a fresh capture comes back empty -- a repair block that repairs nothing.

**Disclosed gaps:** still a protocol rather than a transport (every message is a byte block; binding
them to packet types is a networking work item, and it is what lets the whole sequence be exercised
end to end without a network); snapshots cover terrain heights, because buildings, vehicles and AI
state each already have their own replication path and step 16's readiness gate is what this phase
owes them; generation time is recorded rather than measured here; and the profile and content hashes
come from their real owners rather than being invented.

**What is not proven:** two processes on a real network. The self-check throws the server's world
away, regenerates the baseline deterministically, reconstructs from the blocks alone and compares
checksums -- exactly steps 9-12 minus a socket. The wire itself is stated as outstanding rather than
claimed.

**A speed governor, because scaling throttle alone is not the same as reducing performance.**
Tracked vehicles degrade correctly on throttle scaling (track resistance is linear in speed, so
terminal velocity is proportional to throttle), but wheeled vehicles do not: their top speed is set
by where the engine torque curve falls off at a throttle-independent redline, and the quadratic
drag term that would otherwise cap it defaults to `0.0f`. A damaged wheeled vehicle would have
accelerated worse while still reaching nearly its normal top speed -- cosmetic exactly where it
should bite hardest. `Govern_Subsystem_Speed` withholds propulsion above `engine_factor` x the
fastest ground speed that vehicle has been seen to reach while undamaged, letting the stock physics
decelerate it. Reverse and braking are never touched, and vertical velocity is excluded. The
reference is learned rather than derived because no authoritative per-vehicle top speed exists to
read (`SmartGameObj::Get_Max_Speed` is a hardcoded placeholder `VehicleGameObj` never overrides)
and re-deriving it from gear ratios/torque curve/redline would put a second copy of the
integrator's own model in Combat, free to disagree with it.

freshly computed `StateTimer` by the owning vehicle's efficiency -- the same per-instance,
owner-conditional multiply the adjacent `WEAPON_RATE_CHEAT` block already performs. The shared
`AmmoDefinitionClass::RateOfFire` is never written, so one damaged tank cannot slow that weapon for
every other object using the preset, and the modifier is owner-gated on `As_VehicleGameObj()` so
infantry weapons are untouched. Only the two firing states are affected; reload and switch speeds
belong to whoever carries the weapon. No new state: the efficiency is a derived read taken at the
moment the timer is set. The old binary cut-off survives as `weapon_disable_fraction` but now
defaults to `0` (off), making it the weapon-side counterpart of `allow_immobilize`.

**"No first-player-wins permanent rule" — the one real behavior change.** Before this phase, a
claim against a vacant seat granted instantly no matter how many teammates were connected. Now: a
vacant seat with zero other connected teammates still grants instantly (there is no one to
contest, and it is what keeps solo/skirmish assignment at zero latency); a vacant seat with a real
