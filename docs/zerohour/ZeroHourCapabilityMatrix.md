# The Zero Hour capability matrix

Roadmap Sections 13.2, 13.3 and 3.2. What the donor builds, what each part of
it is, and where the 25 mandatory systems actually live at the pinned SHA.

The pin, the configuration and the exclusions are in
`ZeroHourDonorBaseline.md`. Nothing here is written from memory of the EA-era
layout; every path is resolved against the checked-out donor by a tool, and the
tools fail rather than go quietly stale.

## The one structural fact that shapes every port

OpenW3D and the Zero Hour donor descend from the same Westwood W3D libraries,
and far more of that ancestry survives on both sides than expected:

| Library | Donor files | Also in this tree, same name | Donor-only |
| --- | --- | --- | --- |
| WW3D2 | 232 | 217 | 15 |
| WWMath | 79 | 79 | 0 |
| WWSaveLoad | 33 | 33 | 0 |
| WWDebug | 7 | 7 | 0 |
| WWLib | 164 | 131 | 33 |
| WWAudio | 43 | 33 | 10 |
| WWDownload | 11 | 0 | 11 |
| **Total** | **569** | **500 (87%)** | **69** |

Generated by `tools/zerohour/shared_lineage.py` into
`ZeroHourSharedLineage.tsv`.

This changes what a "port" is. For most of the renderer, the maths and the
whole persistence layer, adapting a Zero Hour capability means diffing two
descendants of one file rather than translating between two engines. It also
means the donor's WWMath and WWSaveLoad hold **nothing to port** — they are a
source of bug fixes, not of features.

The 68 files in `GeneralsMD/Code/Libraries/Source/WWVegas/WW3D2` are the Zero
Hour renderer deltas that TheSuperHackers have not unified into `Core` yet —
`mesh`, `hlod`, `part_buf`, `light`, `scene`, `shader`, `vertmaterial` and
company. **All 68 exist in `Code/ww3d2` under the same name.** That set is the
highest-value, lowest-risk port surface in the entire donor.

## What the Zero Hour configuration builds

`tools/zerohour/donor_surface.py` walks the donor's CMake graph with
`RTS_BUILD_ZEROHOUR` on and `RTS_BUILD_GENERALS` off, and refuses to finish if
a `Generals/` path appears. It reaches **51 directories and 71 targets**
(`ZeroHourDonorSurface.tsv`).

Every one of those directories is classified in
`ZeroHourSurfaceClassification.tsv`, with a written reason, using only the
vocabulary Section 13.2 permits:

```text
17 directories to port
 9 already equivalent in this tree
25 rejected, each with a reason
```

`tools/zerohour/check_surface_classified.py` fails if a built directory has no
classification, if a classification names a directory the donor no longer
builds, if a classification is outside the permitted vocabulary, or if a
rejection has no reason. That is what makes Section 13.2's "no relevant Zero
Hour engine area may remain `UNREVIEWED`" a property of the tree rather than a
claim in a document.

### Where the code turned out to be

Two surprises worth stating, because both contradict the EA-era layout the
roadmap warns against assuming:

- **Most of the terrain and render systems are in shared `Core`, not in
  `GeneralsMD`.** `BaseHeightMap`, `TerrainTex`, `W3DShaderManager`,
  `W3DSmudge`, `W3DSnow`, `W3DTerrainBackground`, `W3DTerrainTracks`,
  `W3DTreeBuffer`, `W3DWater` and the draw modules all live in
  `Core/GameEngineDevice`.
- **Some do not.** Roads, bridges, shroud, projected and volumetric shadows,
  status circles and waypoint buffers are still `GeneralsMD`-only. The
  unification is in progress upstream, and where a system sits today decides
  which tree we read — not a rule about what "should" be shared.

## What is rejected, and why

Recorded per directory in `ZeroHourSurfaceClassification.tsv`; the reasons in
summary:

- **`RETAIL_INFRASTRUCTURE_REJECT`** — WWDownload (retail patcher), the
  EABrowser pair (embedded Internet Explorer), `mangler` and `matchbot`
  (GameSpy NAT and matchmaking), `wolSetup` (Westwood Online accounts), the
  Launcher and its `DatGen`. Services that no longer exist, for a distribution
  model OpenW3D does not use.
- **`SAGE_ARCHITECTURE_REJECT`** — `GeneralsMD/Code/Main`: WinMain, the SAGE
  game loop and its ownership model. OpenW3D keeps its own, and Section 13.7
  rejects SAGE `Thing`/game-loop ownership by name.
- **`NOT_RELEVANT_TO_OPENW3D`** — WorldBuilder and MapCacheBuilder (SAGE map
  format; OpenW3D authors levels in LevelEdit against W3D geometry), GUIEdit
  (SAGE `.wnd` windows), Babylon (the donor's own localisation format, against
  `Code/Strings Editor` and `wwtranslatedb` here), version-stamping tools,
  `timingTest`, the VC6 STLport shim and donor build glue.
- **`OPENW3D_ALREADY_EQUIVALENT`** — WWMath, WWSaveLoad, WWDebug, WWAudio,
  `max2w3d`, `pluglib`, `W3DView`, `wdump`. Same libraries and tools, already
  in this tree; and OpenW3D additionally has a Blender exporter the donor lacks.

Two rejections inside otherwise-ported directories are worth naming here
because a directory-level label would hide them: `Core/GameEngineDevice`'s Bink
and Miles device bindings and its Win32 DirectInput devices are rejected
subparts, and `GeneralsMD/Code/GameEngine`'s faction unit behaviour, generals
challenge and campaign shells, SAGE networking and GameSpy code are rejected
subparts. Both are recorded in the classification file's Reason column.

## No predecessor-game staging

There is no plan, anywhere in this matrix, to build a predecessor-game version
of any system and upgrade it afterwards. Every one of ZH-01 through ZH-40
names its source in `Core` or `GeneralsMD` at the pinned SHA and is adapted
once, from that. `Generals/` is excluded by the donor's own build condition and
by two tools that error if it appears.
