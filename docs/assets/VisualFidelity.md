# Visual fidelity (roadmap Section 52A)

Section 52A's own program-wide constraint: "no new authored art is required... generated
procedurally... recorded in `docs/assets/VisualFidelity.md` as improvements, never
prerequisites." This file is that record.

## Phases 46-50

No entries. Every one of the five phases works from what the engine already computes or
loads -- device capability, the existing per-vertex light solve, the sun's own transform,
a light's own existing `Intensity`/`GroupID` -- or from a level author's own placement
decisions (a `LightPhysClass`'s `Group ID`, associating it with a building). None of the
five needed a texture, model, or any other asset that does not already exist, and none is
blocked on one. See `docs/zerohour/VisualFidelityProgram.md` for what each phase actually
does.

An asset *would* improve, not gate, one of these if it existed:

- A dedicated flicker/pulse/warmup/fail profile authored per light fixture (rather than the
  one fixed timing each curve uses today) would be a data file, not new code -- Phase 50's
  `LightClass::Set_Light_Curve` already takes the curve type as a parameter; only the
  per-curve constants (`FAIL_SECONDS`, the `PULSE` period, and so on) are fixed rather than
  read from anywhere yet. Not a prerequisite for the phase's own acceptance line.

## Phases 51-55

Two procedural, in-memory textures, neither loaded from disk, both prefixed `ow_` for
consistency with the rest of this folder even though nothing here reads either name from the
mix files:

- **`ow_cloud_shadow_mask`** -- Phase 53's ground-shadow density mask. Generated once at
  `CloudLayerClass::Build_Shadow_Mask_Texture` (`Code/Combat/backgroundmgr.cpp`): a 128x128
  tiling value-noise texture, coarse 8x8 random grid bilinearly interpolated and squared so it
  reads as broken cloud cover rather than an even grey wash. An authored replacement --
  hand-painted cloud-shaped density, matching whatever `CloudLayerClass`'s own sky texture
  looks like on a given level -- would be a straightforward drop-in: `Build_Shadow_Mask_Texture`
  would just load it instead of generating it, and everything downstream (the projector, the
  scroll, the multiplicative blend) is unchanged either way. Not a prerequisite; Phase 53's
  acceptance does not ask for a particular cloud shape, only that shade crosses terrain in the
  wind direction.
- **`ow_sun_shaft_glow`** -- *withdrawn.* This was Phase 55's glow sprite, generated by
  `BackgroundMgrClass::Build_Sun_Shaft_Glow_Texture` for the streak-sprite implementation of the
  sun shafts. Phases 56-57 built the render-target post-process chain that implementation was
  waiting for, Phase 55 was reimplemented on it as a real radial blur, and the streak-sprite path
  and this texture with it were deleted rather than left beside the new one. Its role is now
  filled by `ow_bloom_glow` below. Recorded rather than silently removed, so that anybody who
  saw the old name knows where it went.

No other new asset is needed for Phases 51-55. P51 (height fog) and P52 (sky/contact
occlusion) work entirely from geometry and device state already present; P54 (environment
reflections) reuses `MetalMapManagerClass`'s existing procedural generator unchanged, wiring
it into the runtime rather than adding anything new to generate.

## Phases 56-62

One procedural, in-memory texture, not loaded from disk, prefixed `ow_` for consistency with the
rest of this folder even though nothing reads the name from the mix files:

- **`ow_bloom_glow`** -- the soft sprite every glare source is drawn as, and the source the sun
  shafts are blurred from. Generated once at `PostProcessChainClass::Build_Glow_Texture`
  (`Code/ww3d2/postprocess.cpp`): a 32x32 radial falloff, squared for a soft shoulder. Shared by
  Phase 57's bloom and Phase 55's reworked radial streaks, which is the same sharing rule the
  render target itself follows -- one post chain, not two.

  An authored lens-flare-style glow, with the small chromatic fringing real optics give a strong
  backlight, would read better at close range than a flat radial falloff does. It is a texture
  swap only: `Build_Glow_Texture` would load it instead of generating it, and nothing downstream
  (the threshold, the accumulation, the composite taps, the streak anchoring) changes either way.
  **Not a prerequisite.**

No other new asset is needed for Phases 56-62, and three of those phases are worth naming for why
they need none:

- **P59 (wetness)** is a material-parameter ramp. It darkens albedo and lifts specular through
  `SurfaceTintEffectClass` and biases terrain layer weights toward the `TERRAIN_LAYER_CLIFF`-style
  wet variants Section 18's table already defines. It *gains* from a purpose-made wet ground
  texture where one exists -- `TerrainTextureSystem::Define_Layer` takes one -- but needs none,
  because the shoreline layer it biases toward is already in the default table.
- **P61 (damage appearance)** is tint only, by the phase's own constraint: no damage-state models,
  no damage textures, no second material set. It works on content that shipped in 2002 for exactly
  that reason.
- **P58 (wind)** derives sway amplitude from vertex position. No vertex colours need authoring,
  and `FoliageModelCacheClass` measures each model's height itself when it caches it.

## Phases 63-65 (roadmap Section 52B)

No required assets, and one recorded gap that is authoring rather than art:

- **Escarpment faces** are dressed from the existing terrain layer table -- the escarpment's own
  layer index, or the first layer of kind `TERRAIN_LAYER_CLIFF`, which
  `TerrainTextureSystem::Define_Default_Layers` already provides. With no cliff layer defined and
  no texture in the mix files, the face is still built, still collides, and is simply untextured;
  `EscarpmentSystem::Get_Untextured_Face_Count` reports how many. A purpose-made rock face texture
  is an improvement, never a prerequisite. See `docs/zerohour/WorldStructureProgram.md`.
- **Bridge piers and abutments** continue to degrade the way Section 20 already left them: a
  section whose model is unnamed or missing is built as a box of exactly the declared size, which
  collides, carries and breaks. Phase 64 added deck height, stated clearance and abutment heights;
  it added no new model slot.
