## 1. Staging location — deviation from roadmap Section 7

Roadmap Section 7 asks for the official `source-4.8.4.zip`, an exact MD5
verification, preservation of the untouched archive, and extraction into
`third_party/tt484_source_reference/`.

What actually exists: the user supplied the TT source directly as `tt_4.8.4/` in the
repository root. **No official archive is present, so the MD5 verification step
could not be performed.** The directory is treated as the Phase 1 staging/reference
copy in place; it has not been moved to `third_party/tt484_source_reference/` to
avoid churning thousands of files without instruction.

Version evidence: `tt_4.8.4/scripts/engine_common.h:18` declares
`#define TT_VERSION ((float)4.8f)`. The directory was renamed from `tt_4.9.4/` to
`tt_4.8.4/` by the user after this mismatch was raised (resolved Q-001).

Consequence to record in provenance: the TT donor is identified by directory
contents and the in-source version constant, not by a verified archive checksum.

Roles are assigned from the destination directory wherever that is decisive — a
file landing in `Code/wwphys` is a physics/collision API file whatever else it
mentions. Content signals are consulted only for the general-purpose destinations
(`Code/Combat`, `Code/Commando`) and are scored by match count, not first hit.
`render/shader integration`, `physics/collision API` and `save/load` are
deliberately **not** content signals: `RenderObjClass`, `PhysClass` and
`ChunkSaveClass` appear as members or parameters throughout the gameplay tree, and
scoring on them labels most of `Code/Combat` by whatever it happens to hold a
pointer to. An earlier revision of this pass did exactly that and reported 185
`save/load` files.

**What the two fallback buckets now mean.** `engine wrapper/API` (383) is no longer
a shrug. It is assigned only where the file resolved to an OpenW3D owner by symbol
identity, which is what the role describes: TT's own declaration of an engine class
that OpenW3D already owns. `utility` (249) is the genuine residue — a file with a
destination but no symbol-level tie to it.

### 2.3 Dispositions for the four undecided areas

Section 2.1 left `VFS/`, `MemoryManager/`, `teamspeak/` and `bansystem/` marked
"evaluate". They are decided here.

**`MemoryManager/` (13 files) -> `Code/wwlib`.** TT's `FastAllocatorGeneral` /
`FastFixedAllocator` / `MemTracker` supersede the stock allocator, and OpenW3D
already declares `Code/wwlib/FastAllocator.h`. Per the non-negotiable merge rule the
TT implementation folds into that canonical owner and the stock path is removed.
Note that `Code/fastalloc_test/MemoryManager/` currently holds a verbatim copy of
this same TT tree as a standalone test harness; it is not a destination, and
`files2.py` excludes it from candidate lookups for that reason.

**`VFS/` (73 files) -> DROP.** The VFS is a standalone out-of-process filesystem
provider: a COM class factory, a WinInet namespace registration, an RPC server and
client, AES and MD5, and its own reimplementations of `StdLib`, `Memory` and
`Lists`. None of that survives a native merge. The part with engine meaning is not
in `VFS/` at all — it is the consumer seam in `tt/`: `VfsFile` subclasses
`FileClass` and `PackageManager` subclasses `FileFactoryClass`. Those six files are
mapped to `Code/wwlib`, where OpenW3D's existing mix/file factory already provides
the same seam. Package mounting is therefore a `Code/wwlib` file-factory feature,
not an imported DLL.

**`teamspeak/` (6 files) -> DROP.** A TCP client that drives an external TeamSpeak
process. Out of engine scope.

**`bansystem/` (10 files) -> `Code/wwnet`, deferred.** `BanList`, `BanListStore` and
`IpAddress` are a server-only feature enforced at connection acceptance, which is
the same seam as `ConnectionAcceptanceFilter`. It belongs with the dedicated-server
work (P44/P47), not with Phase 2.

> **Correction, 2026-08-21.** A first pass reported 126 TT scripts and 3 collisions.
> That was wrong. It searched only for `REGISTER_SCRIPT(...)`, but TT's dominant
> registration form is the raw template instantiation, and the **string literal** is

> below come from a corrected extractor that handles both forms.

TT registers scripts two ways:

```cpp
// A) dominant form — the STRING is the script name
ScriptRegistrant<JFW_Building_Gun> JFW_Building_Gun_Registrant(

REGISTER_SCRIPT(M10_Turret, "");
```

### 4.1 `REF_DEF2` / `REF_DECL2` / `REF_DECL` — data binding (Phase 2)

### 4.3 The hooks are self-describing — that is what makes Phase 3 tractable

Two properties of the TT tree do most of Phase 3's analysis work in advance:

- **694 of the 760 sites carry an inline intent comment** naming what the patch does.
- **626 sites name the TT function that replaces the stock one**, e.g.
  `hookAsJump(0x00577A80, 0x00000000, MeshClass::Render)`. Across the in-scope set
  these resolve to **507 distinct TT symbols**.

The named-replacement form is decisive: TT overwhelmingly names its replacement
after the stock function it displaces, so the OpenW3D owner is found by symbol
lookup rather than by disassembling addresses. Only the 129 `WriteMemory` /
`WriteNop` / `VirtualProtect` byte-patch sites lack a symbol, and all but a handful
of those carry an intent comment instead.

### 4.4 Direct `VirtualProtect` outside the helper

`tt/WeaponClass.cpp:61-62` patches `0x007E42E4` / `0x007E42E0` inline rather than via
`hooksupport`. Flagged so Phase 3 does not miss it by only auditing the helper API.

### 4.5 `PacketManagerClass` — 57 sites, 2 logical patches

`ttinit/PacketManagerClass.cpp:_placeHooks()` looks like the second-largest hook
cluster in the tree. It is not. Every one of its `WriteMemory` calls rewrites the
operand of a stock `mov ecx, PacketManager` instruction to point at TT's own
`PacketManager()` singleton, once per reference site, duplicated across the two
executable variants (`Exe == 0` Game.exe, `Exe == 1` FDS). A 58th call zeroes the
stock static constructor.

Logically this is a single decision — *TT replaces the stock `PacketManagerClass`
singleton wholesale* — plus *suppress the stock one's construction*. In a source
merge both vanish: TT's implementation becomes `Code/wwnet/packetmgr.cpp` and every
reference binds at link time. **Estimated Phase 3 cost: near zero, despite the site
count.**

### 5.7 Parser correction to the 5.6 survey

`ttparse` matched one physical line at a time. Real headers do not cooperate.
OpenW3D wraps long signatures — the five-argument `RenderObjClass::Set_Animation`
spans four lines, `PhysicsSceneClass::Add_Camera_Shake` four — and TT sometimes
leaves an inline body's opening brace on the line after the signature, as in
`AirFactoryGameObj::Set_Busy`. Either way `METH` saw a fragment, so the same
member could read as absent on the OpenW3D side and TT-only on the TT side, and
the delta reported work that was already done, or missed a TT declaration
entirely.

`ttparse.logical_lines` now joins a line to its successors while its parentheses
are open, then pulls in a following line carrying only a trailing qualifier or
the opening brace. Two stray backspace bytes in `DECORATOR` — a heredoc ate the
word-boundary escapes when the file was first written, leaving a pattern that
could never match — are fixed in the same pass.

Net effect on the survey, over and above the merges already landed: five rows
were false positives and are gone (`RenderObjClass::Set_Animation` ×2,
`SceneClass::Compute_Point_Visibility`, and `PhysicsSceneClass`'s `Create_Decal`,
`Optimize_LODs`, `Shatter_Mesh`, `Add_Camera_Shake` — the last four are on
OpenW3D's own `PhysicsSceneClass`, not owned elsewhere); two TT declarations that
had been invisible are now counted (`AirFactoryGameObj::Set_Busy`,
`NavalFactoryGameObj::Set_Busy`).

So `PhysicsSceneClass` is *not* the outlier 5.6 makes it out to be at the
declaration level — its "elsewhere" column is zero because nothing was owned
elsewhere, and six methods remain to write, still all shadow and polygon-budget
control. The sequencing conclusion is unchanged: that is P20's subject matter.

Treat `TTMethodSources.tsv` as the live figure; 5.6's table is the historical
starting state and is not maintained.

### 5.10 Save/load reconciliation notes

Three findings from wiring the new types through `wwsaveload`:

- **Chunk IDs are persisted, so new ones append.** The first pass inserted the new
 `CHUNKID_GAME_OBJECT_*` values after `CHUNKID_GAME_OBJECT_DEF_REPAIR_BAY`, which
 renumbered `CHUNKID_MAPMGR`, `CHUNKID_ENCYCLOPEDIAMGR` and the Mendoza/Raveshaw
 boss IDs by eight and would have broken every existing level and save file. They
 now sit at the end of the game-object run, with a comment saying why. The
 `CLASSID_GAME_OBJECT_DEF_*` values were already appended and needed no change.
- **A new type must be force-linked or it does not exist.** `combat` is a static
 library, so the linker only pulls an object file something references. The
 definition factories are file-scope statics with no external references;
 `Force_Link_Combat` in `objlibrary.cpp` is what drags them in. Both new types are
 now in that list — without it the presets register nowhere and fail to load.
- **TT's numeric IDs are unrecoverable and not matched.** TT never shipped
 `combatchunkid.h`; its values for these four types live in the closed binary. TT
 would have had to append after the same stock last value we did, so the allocation
 is probably close, but nothing here depends on matching it — directive 0.4 and
 the P02 "no obsolete ABI constraints" rule mean TT-authored preset databases are
 not a compatibility target.

## 7. Architectural notes carried into later phases

- **`shaders/` is excluded outright.** 317 files, ~9281 address literals. Directive
  0.6 forbids importing TT's D3D8-to-D3D9 translation DLL; OpenW3D is already
  D3D9-backed.
- **The binary-plugin sample projects are excluded.** Directive 0.5 forbids a binary
  plugin compatibility layer in this roadmap.
- **The injector/proxy architecture is discarded**, not ported. `ttinit/` exists to
  inject into a closed `Game.exe`; a native build has no such need (directive 0.4).
- The 210 `REF_DEF2` bindings are the clearest evidence that most of TT's "address
  soup" is a symptom of closed-binary linkage, not genuine behavioral complexity.
  A native merge deletes them rather than translating them.
