GMAX TO W3D EXPORT GUIDE
========================

Scope
-----
This guide is the job list the GMax batch exporter reads. Every line below is one
.gmax scene and the W3D export type it must be exported with; a scene absent from
this guide is a scene BatchExportMPBuildings.ms never compiles.

Inventory refreshed on 2026-08-13 and contains 299 entries. Paths below are
relative to models\.

NOT EVERY .gmax UNDER models\ IS LISTED, ON PURPOSE. "more buildings\" is out of
scope for this guide and is deliberately not batch exported. Everything else
under models\ is covered in full.

W3D exporter choices
--------------------
Renegade Terrain
  Exports static geometry as terrain and uses terrain/collision optimization.
  Use this for building shells, interiors, floors, pads, shafts, strips,
  bunkers, and other static geometry that players or vehicles can collide with.

Hierarchical Animated Model
  Exports geometry, hierarchy/skeleton, and timeline animation. Use this for
  doors, elevators, lifts, aggregate (_ag_) scenes, construction/destruction
  sequences, moving machinery, animated effects, and other moving components.

Hierarchical Model
  Exports geometry and hierarchy/skeleton without timeline animation. Use this
  for static objects whose node hierarchy, pivots, light nodes, or named special
  nodes must survive export.

Simple Mesh
  Exports geometry only. Use this for standalone static props that do not need
  a hierarchy, animation, or terrain-style building collision handling.

Skeleton
  Exports only the hierarchy/skeleton. None of the current source files should
  be exported with this option.

Pure Animation
  Exports only animation data for an existing hierarchy, so the hierarchy has to
  be exported separately and the animation played back against it. Used by
  m_turret_shot, whose skeleton is b_turret_top -- export b_turret_top first.

Building assembly requirements
------------------------------
1. Keep every component of one building at the same building-space origin.
   Do not center each exterior, interior, door, elevator, aggregate, or effect
   separately before export. The runtime can then place every W3D at the same
   transform and the pieces will line up.
2. Preserve the authored pivots and parent/child links for doors, elevators,
   lifts, construction parts, destruction parts, and machinery. Do not reset a
   moving part's pivot after its animation has been authored.
3. Export static exterior/interior geometry separately from animated parts.
   Do not merge doors, lifts, or other moving meshes into a Renegade Terrain
   export.
4. Purchase terminals, MCTs, and other LevelEdit preset proxies must retain
   their named nodes. Use the LevelEdit aggregate naming form
   PresetName~unique, for example GDI_Purchase_Terminal~01. The text before '~'
   is the preset name LevelEdit resolves; the text after '~' only makes the node
   name unique. Do not merge purchase-terminal or MCT proxy boxes into terrain.
5. Keep terminal/MCT proxy positions in the same coordinate system as the
   building. A proxy belongs in the appropriate aggregate/hierarchical W3D, or
   the equivalent transform must be recorded in the building JSON. The visible
   terminal model and the interaction preset/box are separate responsibilities.
6. Set collision flags/materials deliberately before exporting. VIS, VISX,
   TEMP, TMP, and blocker sources are authoring helpers unless a map/building
   pipeline explicitly consumes them. Do not add them to the normal runtime
   building component list merely because a W3D was produced.
7. Export the runtime file with the same basename and a .w3d extension unless
   the building JSON intentionally assigns another filename.
